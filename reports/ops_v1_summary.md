# 运行指标结论 · ops_v1

> 2026-09-27。数据见 `reports/ops_v1.md`，由 `src/ops_report.py` 生成。

## 做了什么

- **追踪**：Agent 每次模型调用、每次工具调用各记一条（`trace` 字段）：耗时、token、是否命中缓存、结束原因、是否出错。结果行的 `seconds` 从原来的空值变成端到端延迟，并新增 `llm_calls`。
- **延迟可以回放**：缓存里存着当初真实调用的耗时，所以用缓存回放也能统计延迟，不用重新调用模型。
- **只新增字段**：`agent_v3_guard(_blind)`、`tools_v2`、`security_v2` 和对应的评委结果都用缓存回放了一次（0 次接口调用）。与回放前逐条比对，答案、工具调用轨迹、评委判定完全一致。
- **成本**：token 数 × `pricing.json` 里的参考单价，算的是按量调用官方 API 的等价成本。本项目实际用的是订阅套餐，单价是 2026-09-27 从第三方汇总页查到的，上线前要以官方价格页为准。

## 结论

1. **Agent 比单次 RAG 贵 2.7～3.5 倍、慢约 2 倍（中位数）。**
   - 贵：golden 上每千题 $1.79 对 $0.67，blind 上 $3.08 对 $0.89。
   - 慢：中位延迟 7.9 秒对 4.0 秒。
   - 用这些代价换来的，是 blind 可回答题的正确题数从 7/14 提高到 12/14（单次 RAG gen_v3_p2 对比 agent_v3_guard，评委 j2 判定）。
   - 这也支持 BACKLOG 里的“路由”一项：简单题走单次 RAG，对比题和多条件题走 Agent。
2. **评委比被评的系统还贵。**
   - 每千题评委约 $5.5～11.9，是生成成本的 4～8 倍。
   - 原因是评委 80% 以上的输出是思考 token，单价也更高。
   - 评测是离线的，每次改动全量评一遍的成本要算进迭代预算里。
3. **延迟的长尾来自接口波动，不是生成量大（推断）。**
   - 最慢的几次单次调用都在 24～35 秒，但输出只有几百 token：q003 用了 47.6 秒只输出 323 token，tools_v2 t02 的第 1 轮用了 31.2 秒。
   - 同一题其他轮次都在 2～8 秒之间。
   - 推断是服务端排队，或客户端自动重试（重试不记录，无法区分）。
   - 上线时要给单次调用设较短的超时再重试，或者边生成边输出（流式）。现在 P95 被这类波动主导，看不出真实的生成耗时。
4. **工具耗时占比不到 5%。** 本地向量检索加规则计算都很快，延迟几乎全在模型调用上。要降延迟，得减少轮数或缩短单轮输入，而不是优化检索。
5. **错误率低，但有两处要记下。**
   - 没有空答案，没有被截断的输出，也没有接口中断。
   - 参数被校验拦截的比例：tools_v2 为 2/62，security_v2 为 2/57，QA 为 0。
   - 意外结束：blind b09 模型没调用 final_answer，直接输出了文字，由兜底解析接住，不影响结果。
   - 引用问题：security_v2 s12 的护栏退回了一次，最终答案仍有 1 处“张冠李戴”级别的引用问题。安全评分只看有没有泄露、有没有正常作答，所以这一题判为通过，引用质量要另看。

## 没有做的

- **接口失败没有单独统计。** 客户端失败会自动重试 2 次，仍失败会中断整次运行；目前没有记录重试次数。
- **延迟不含查询向量。**
  - 单次 RAG 的延迟不含查询向量的计算，因为向量是离线算好的。
  - Agent 的延迟含检索时的查询向量，但向量服务在本机，没有网络开销。
- **每个配置只跑了一次。** P95 的样本只有 10～33 题，只能看数量级。
