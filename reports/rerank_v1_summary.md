# 重排实验 · rerank_v1

> 2026-09-26。bge-reranker-v2-m3（本地 GPU，fp16），对向量检索（bge-m3）的前 N 名重新排序。
> 分数由 `src/rerank.py` 在 Miniconda 里离线计算：51 题 × 565 块，共 255 秒。
> 端到端沿用上下文扩展 + 提示词 p2 + 评委 j2，只把检索换成“向量粗选 + 重排”。

## 事前规则与预测

- N 只看 golden_v2 来选，盲测只用来验证。
- 预测：盲测的 Recall@5 明显上升，b04、b18 等跨条款题有改善。

## 检索指标

| | golden_v2 Hit@5 / Recall@5 / MRR | 盲测 Hit@5 / Recall@5 / MRR |
|---|---|---|
| 向量检索 | 93.3% / 91.1% / 0.859 | 85.7% / 57.6% / 0.649 |
| 重排前 20 名 | 93.3% / 91.1% / 0.836 | **92.9% / 65.8% / 0.726** |
| 重排前 50 名 | 93.3% / 91.1% / 0.834 | 92.9% / 69.4% / 0.726 |
| 全部重排 | 90.0% / 87.8% / 0.828 | 92.9% / 69.4% / 0.726 |

按规则选 N=20（golden 上 20 和 50 的 Hit、Recall 持平，MRR 20 略高）。全部重排反而更差，说明“粗选 + 精排”的两阶段是必要的。

## 结论（AI 建议）

1. **检索指标的提升没有转化为答案质量。** 盲测 Recall@5 提高 8 个点，但端到端只多对 1 题，还多错 1 题，并第一次出现了不忠实的答案。
2. **重排改变了哪些题失败，而不是减少失败。** 它提上来一些证据，也压下去一些证据；而真正缺的证据（b04 的 8.2 排第 43、b12 的 2.4.4 排第 61、b03 的第九条第 6 块）在前 20 名之外，重排够不着。
3. **单次查询的检索已经到瓶颈。** 一个问题需要多个条款时，一次查询的排序很难把它们都排进前几名。这正是第 5 周 Agent 要解决的：先回答、发现缺信息、换个说法再查。
4. **决定：不把重排设为默认**（golden 上正确数 28 → 27，按规则不采用）。代码保留，`--rerank` 可以随时打开。
5. **提示词规则不是万能的**：b05 说明，只要把误导性的内容（投保举例）排到前面，p2 的“区分规则与举例”也会失效。检索质量和提示词是一起作用的。

## 局限

- 盲测已经参与了多次决策（p2、重排），不再是独立的检验。
- 每个配置只跑一次；一题的差异可能是噪声。
