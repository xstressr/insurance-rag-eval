# 路由 v1 协议（先提交，后在验证集上运行）

> 2026-09-27 写定。本文件与 `src/route.py` 一起提交，提交时还没有在 blind_v2.1、v3 或 v5 上运行过路由。

## 规则

规则只在开发集（golden_v2 和 golden_blind_v1，共 51 题）上设计：

- **shape（按问题形态）。** 满足任一条件就直接走 Agent：
  - 问到 ≥2 款产品；
  - 含对比词（哪个、区别、分别……）；
  - 一句话里有 ≥2 个问号。
  - 注意：“问号 ≥2”这一条的想法来自 v3 的结果，所以 shape 在 v3 上的成绩不算独立证据。
- **cascade（级联）。** 先跑单次 RAG。它拒答了，或者答案里有“无法回答、片段未、未提及、未约定……”这类承认材料不够的说法（正则 `INSUFFICIENT`），就改用 Agent。这组词是看着开发集的答案定的，所以开发集上的结果偏乐观。
- **shape_or_cascade（两者合用）。** 满足任一条就走 Agent。

## 开发集结果（设计时已看过）

见 `reports/route_dev.md`。cascade 可回答题答对 42/44，与理论上限相同；全部走 Agent 是 41/44。cascade 的成本是全部走 Agent 的 80%，中位延迟最高（10.2 秒）。

## 预测（在验证集上运行之前写下）

1. cascade 的可回答题答对数，不低于“全部走 Agent”减 1 题。
2. cascade 的成本低于“全部走 Agent”的 85%。
3. shape 在 v3 上接近“全部走 Agent”（因为 v3 的题多数连问好几件事）；在 v2.1 上接近“全部走单次 RAG”。
4. cascade 的中位延迟高于其他所有策略。这是它的主要代价。

## 验证顺序

1. blind_v2.1 + v3（这两个集合启发了路由的想法，只能算半确认）。
2. 全新的 blind_v5：按 `dataset/blind_v3_protocol.md` 的做法换一批出题模型出题，先锁定再标注，然后两套系统各跑一次，再评估路由。只有这一步是独立检验。

规则在验证集上跑过以后不再修改；要改就升为 route_v2，并换一批新题验证。
