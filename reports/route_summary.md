> 2026-09-27。脚本 `src/route.py`（v1）、`src/route_llm.py`（v2）。
> 协议：`reports/route_v1_protocol.md`、`reports/route_v2_protocol.md`。
> 明细：`reports/route_dev.md`、`route_v1.md`、`route_v2_design.md`、`route_v1_on_v5.md`、`route_v2_on_v5.md`。

## 问题

单次 RAG 便宜，但一句话里有多问时常常答不全；Agent 答得全，但要贵约 2.5 倍。能不能每题自动选一条路，只在需要时用 Agent？

## 做法

评估是离线的。两套系统对每道题的答案和评委判定都已经有了，路由只需要按规则逐题选用其中一个，成本和延迟按实际会发生的调用累加。

| 路由 | 规则 | 在哪些题上设计 | 在哪些题上检验 |
|---|---|---|---|
| v1 · shape（按问题形态） | 问到多款产品、带对比词，或 ≥2 个问号 → Agent | 开发集（51 题） | v2.1 + v3（半确认）、v5（独立） |
| v1 · cascade（级联） | 先跑单次 RAG；拒答或答案里说“片段未提及”一类的话 → Agent | 同上 | 同上 |
| v2 · llm_post（答后检查） | 先跑单次 RAG；判断模型检查答案有没有漏掉子问题 → Agent | 开发集 + v2.1 + v3（87 题） | v5（独立） |
| v2 · llm_pre（答前分流，对照） | 判断模型只看问题，决定走哪条路 | 同上 | v5 |

- 每套规则都在检验集生成之前提交。
- blind_v5 由 mimo-v2.6-pro、hy3、grok-4.7 出题，按同一套协议机械抽样 20 题，是这次唯一的独立检验。

## 结果（blind_v5，17 道可回答题 + 3 道拒答题）

| 策略 | 可回答题答对 | 走 Agent 的题 | 美元 / 千题 | 中位延迟 |
|---|---|---|---|---|
| 全部走单次 RAG | 8/17 | 0/20 | 0.95 | 7.0 秒 |
| **全部走 Agent** | **14/17** | 20/20 | **2.40** | **13.3 秒** |
| v1 shape | 9/17 | 6/20 | 1.35 | 8.7 秒 |
| v1 cascade | 14/17 | 14/20 | 2.63 | 17.4 秒 |
| v2 llm_pre | 14/17 | 17/20 | 2.39 | 17.3 秒 |
| v2 llm_post | 13/17 | 6/20 | 2.37 | 20.1 秒 |
| 理论上限（事后挑最优） | 14/17 | 6/20 | 1.35 | 9.3 秒 |

拒答题所有策略都是 3/3，忠实度都是 100%。事先写下的 4 条预测全部成立，见 `route_v2_protocol.md`。

## 结论

1. **在独立检验集上，没有一种路由比“全部走 Agent”更划算。** 准确率最多打平，成本打平或更高，延迟都更长。
2. **原因主要是结构，而不是判断不准。**
   - llm_post 在 v5 上判得很准：升级的 6 题，单次 RAG 都确实没答全（精确度 100%）；该升级的 6 题里只漏了 e19。
   - 但级联的成本等于“单次 RAG + 检查 + 被升级题的 Agent”。单次 RAG 约占 Agent 成本的 40%，大部分是模型的思考 token；检查约占 17%。每题都要付这两项，这批题又有约三成本来就需要 Agent，所以省不下钱。延迟则是三段依次相加。
3. **想接近理论上限，得在答题之前就判断对。**
   - 理论上限（$1.35）的前提是一开始就知道走哪条路。
   - 答前分流只看问题，判断不准：v5 上 20 题送了 17 题去 Agent，开发集上反而丢了 3 题。
4. **题目分布决定路由值不值。** 模型出的题（v3、v5）多数一句话连问好几件事，路由省不下钱；单点问题为主的 v2.1 上，v1 shape 与全部走 Agent 一样答对 10/12，成本只有后者的 39%（$1.29 对 $3.28）。
   - 真实用户的问题分布我们没有测过。
   - 所以现在的建议是：没有真实流量数据之前，全部走 Agent，最简单，延迟也最低；有了真实流量分布以后，再用 llm_post 按这里的方法重新评估。
5. **v1 的教训。**
   - 用关键词判断“答案承认材料不够”，误升级太多：答对的答案里也常顺带写一句“片段未提及”。
   - 只数问号，会漏掉“可以吗，要咋操作？”这类一句两问。

## 比路由更值得试的方向

路由解决的是“选哪条路”，但单次 RAG 的根本问题是：一次检索只拿到第一个子问题的证据。更直接的办法是让单次 RAG 自己把问题拆开：一次调用把问题拆成子问题，每个子问题各检索一次，再合在一起生成答案。

这样仍然只有 1～2 次模型调用，有机会用接近单次 RAG 的成本，拿到接近 Agent 的完整度。已记入 BACKLOG。

另外两个降成本的方向：
- 把检查模型的思考关掉，或换更小的模型；
- 单次 RAG 和 Agent 同时跑，按检查结果决定采用哪个答案。这样延迟只取两者中较慢的那个，但成本不会降。

## 局限

- v5 只有 20 题，理论上限和各策略之间差 1～2 题都在噪声范围内。
- 所有检验集都是模型出的题，不一定代表真实用户的问题分布。
- 成本按 API 列表价换算。
